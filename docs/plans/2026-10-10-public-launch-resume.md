## 阶段一：恢复真实隔离构建与候选发布链

### 输入与所有权

阅读主接续文档及 `docs/plans/2026-10-03-admin-runtime-integration.md`，再直接追踪受限 builder、请求客户端、发布执行器及相应测试。必要修改限于构建/发布阻断、候选打包与对应文档；不切换正式后台、DNS、主站或媒体策略。

### 执行步骤

1. 重新确认本地差异、实际服务器连接方式、当前 builder 服务状态、固定镜像摘要与源码输入。仅读取受保护 SSH 配置，不展示私钥。旧记录称 builder 已停止，必须现场核对。
2. 先核对日志、输入协议、请求大小、流式上传、资源门和入口诊断，定位 422。历史请求约 1 秒即拒绝，未出现 Docker create/start；不得先假定是 MDX 内容错误或资源不足。
3. 延用既有低额度：任务内存 768MiB、总 memory-swap 1280MiB、0.5 CPU、192 PID、10 分钟；启动前可用内存至少 1152MiB。宿主余量低于 384MiB、原服务异常、OOM、超时、磁盘/输出超限即停止本任务容器。另需核对父 slice 限制。资源不足时报告具体缺口，不提高额度、降低门槛、停止无关服务或修改全局 swap/drop_caches。
4. 修复实际协议或实现问题，补最小定向验证。使用真实候选源码和真实 MDX 进入受限服务并产出可检查预览，记录容器隔离、退出状态与产物摘要。fixture 或固定镜像存在不能代替这项证据。
5. 从当前源码生成完整后台候选包，保持 Node/libc/原生依赖一致；复用固定依赖仅在输入匹配时成立。不得拼接旧 index 或重复初始化历史联调数据库。
6. 在隔离目标验证预览、发布执行器和 release 协议；需要 Git 副作用时只使用与正式远端隔离的测试目标。正式 Git/服务器完整发布留阶段四验收，不能将隔离成功写为正式成功。

### 验收与交付

- 明确 422 根因及修复证据；至少一次真实受限 MDX 构建/预览成功，相关检查通过。
